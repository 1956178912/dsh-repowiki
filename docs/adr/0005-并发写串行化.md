## 2026-11-27 决策：并发写操作在进程内按资产根串行化（O5）

- 背景：phase-16 独立代码评审的 O5 指出，8 个工具共享同一份 `ctx.fs`
  资产树，宿主一旦并发调用工具（并行工具调用，或多会话落在同一目录），
  "读旧索引 → 改 → 写"之间会交错：两次 `repowiki-index` 会各自读旧索引
  再互相覆盖；`repowiki-memory` 的 accept/reject 并发会丢掉一次状态写。
  v0.32.0 当时按"单会话顺序调用"的假设接受；本版把该假设升级为机制。

- 选项 A：维持约定，不做锁。实现零成本，但并发调用下仍是已知数据竞争。
- 选项 B：文件系统锁（lockfile / flock）。可跨进程，但需要处理 stale lock、
  超时清理、权限与跨平台差异；DSH 插件运行在同一 Host 进程，跨进程不是
  当前真实需求。
- 选项 C（选择）：进程内 per-root promise 链锁。互斥维度为解析出的资产根
  绝对路径；同根写操作按到达顺序排队，不同根互不阻塞；零依赖、零持久化。

- 理由：用最小机制消除已知的真实竞态；不引入 lockfile 的清理复杂度；
  多工作区（不同根）保持并行，不影响性能。

- 实现：`src/lock.js`（`withLock` / `withAssetRootLock` / `pendingLocks`）。
  接入写路径：`repowiki-index`、`repowiki-extract`、`repowiki-generate`、
  `repowiki-import`、`repowiki-edit`、`repowiki-memory`（write/accept/reject）。
  只读路径（`repowiki-cards`、`repowiki-export` 快照读取、memory list）不加锁，
  保持检索即时；导出与写入并发时的快照可见性与既有 O3 语义一致。

- 影响范围：6 个写工具的执行序；`index.json` 等资产格式不变，无迁移。
  回归见 `test/lock.test.js`（原语语义 + 工具接线）与
  `test/tool-llm.test.js`（extract/generate 的锁外派发与写前二次判定）。

### 修订（v0.44.0）：锁只保护"判-写"临界区，不跨越 LLM 派发

- 背景：整轮持锁使 extract/generate 的模型调用期间，同根其它写工具全部
  排队；子代理回调本插件写工具时会等到自身超时（见下方原"已知限制"）。
  v0.44.0 把"同一时刻只有一个写者"收窄为"同一时刻只有一个写盘者"。

- 修订后语义：
  - extract：读索引/计划/现有卡片与逐候选的 LLM 调用均在锁外；每个候选
    拿到结果后进入 `withLock(root, ...)`，在临界区内重新读取该文件卡片，
    重新判定 fresh / `manuallyEdited` 保护，再写卡；写入清单同样在锁内
    重新枚举卡片。
  - generate：卡片汇总与模型调用在锁外；写页、slug 去重、清单落盘在同一
    临界区完成。
  - index/import/edit/memory 保持整段锁（它们的临界区本身很短且无 LLM）。

- 取舍：并发写者可能为同一文件重复支付一次 LLM 成本；写前二次判定保证
  只有一份结果落盘，且人工修订永远优先。相比让同根所有写工具长时间排队，
  该成本更可接受，也避免子代理回调写工具的自超时死等。

- 回滚：恢复 extract/generate 的整轮 `withAssetRootLock` 包裹即可。

- 已知限制：
  - 仅覆盖本插件进程内的并发；不跨进程、不替代 fs 层原子性；
  - 并发写者可能重复派发同一文件的 LLM 调用（结果不会重复写入）；
  - 排队中的工具不感知取消信号，锁释放后其函数体仍会执行（长跑工具
    自身已有逐项 abort 检查）。

- 回滚方案：删除各工具中的 `withLock` / `withAssetRootLock` 调用（无持久化
  状态、无迁移），即回到 v0.42.0 的并发行为。
